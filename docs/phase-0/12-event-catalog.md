# Phase 0 Event Catalog

Scope amendment (2026-10-06): [ADR-011](../decisions/ADR-011-seller-fulfilled-marketplace.md) and [revised scope](22-scope-phasing.md) control this historical baseline. Warehouse, fleet, platform-owned stock, platform goods/COD custody, and unconditional settlement requirements are OUT_OF_SCOPE. Seller stock reservations, seller order processing, delivery visibility, and applicable controls remain required. Authorized safe implementation may proceed; excluded capabilities and older blanket implementation stops do not create release blockers.

**Status:** proposed asynchronous contract  
**Delivery:** at least once through transactional outbox and durable broker  
**Consumer rule:** every handler must be idempotent even when the catalog marks retry as `No`; duplicated delivery is always possible.

## 1. Canonical envelope

```json
{
  "eventId": "01J...",
  "eventType": "order.created",
  "eventVersion": 1,
  "occurredAt": "2026-10-02T14:30:00Z",
  "producer": "orders",
  "aggregateType": "order",
  "aggregateId": "01J...",
  "aggregateVersion": 3,
  "correlationId": "01J...",
  "causationId": "01J...",
  "actor": { "type": "CUSTOMER", "id": "01J..." },
  "data": {}
}
```

Event data contains the minimum stable fact needed by consumers, not an unrestricted database row. Sensitive seller documents, passwords, OTPs, tokens, PAN, CVV, PIN, full provider authentication payloads, private evidence, and unnecessary personal information are prohibited. Consumers fetch additionally authorized details through a module read port when required.

## 2. Publication, ordering, retry, and schema rules

- The producer writes the domain change and `platform.outbox_events` in the same PostgreSQL transaction.
- The dispatcher publishes by `eventId`; a consumer records `(consumerName,eventId)` before or atomically with its effect.
- Ordering is guaranteed only within the documented aggregate key, such as order ID, payment ID, shipment ID, return ID, or seller ID. `aggregateVersion` lets consumers detect a gap and retry/rebuild.
- `Retry = Yes` means transient failures use bounded exponential backoff with jitter and then a dead-letter queue. Operational alerts include event ID, consumer, attempt count, safe error code, and correlation ID.
- `Retry = No` is limited to advisory telemetry that may be dropped after durable intake; the producer still uses the outbox when it originates from a transaction.
- Breaking payload changes create a new `eventVersion`. Consumers accept current and declared previous versions during migration.
- Replays use the original `eventId` and do not bypass inbox deduplication. An intentional recomputation command receives a new command ID and, if it produces a new fact, a new event ID.

## 8. Analytics event family

The following are behavioral analytics facts sent to the isolated analytics pipeline: `page_view`, `search`, `search_result_click`, `product_view`, `add_to_cart`, `remove_from_cart`, `checkout_started`, `address_selected`, `shipping_selected`, `payment_selected`, `order_placed`, `payment_success`, `payment_failure`, `order_cancelled`, `return_requested`, `purchase_completed`, and `seller_product_created`.

Their common payload is `AnalyticsEventV1 { eventId, occurredAt, sessionId, subjectPseudonym, application, locale, eventName, entityRefs, context }`. It excludes raw email, raw phone, complete address, private evidence, credentials, and payment authentication data. Durable intake deduplicates by `eventId`; downstream aggregation may retry, but customer transactions never wait on analytics availability.

## 9. Consumer acceptance checklist

Before a consumer is enabled in production it must demonstrate:

1. duplicate delivery causes no duplicate financial, stock, notification, provider, or state effect;
2. out-of-order events are rejected, deferred, or safely projected using aggregate version;
3. retryable and terminal failures are classified without exposing sensitive payloads;
4. dead-letter alert and authorized replay procedure exist;
5. metrics cover latency, attempt count, lag, deduplication count, terminal failure and last successful event time;
6. schema compatibility tests pass for supported event versions;
7. reconciliation can detect missing or divergent effects for critical payment, refund, shipment, inventory, COD and settlement consumers.
